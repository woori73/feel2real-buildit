# 대화 수정 응답 지연 개선 설계 (제안 — 구현 없음)

> 근거: 2026-10-13 Muse Spark 실측(`docs/BUILDIT_ASSISTANT_AI_EVAL_20261013.md`, 평가 PR)과 규칙 해석기 오프라인 비교.
> 이 문서는 설계·비교만 담으며 코드 변경은 하지 않는다. 구현은 별도 승인 후.

## 1. 문제
- 수정 한 번의 서버 AI 시간: p50 6~14초, p95 16~44초(복합 요청이 가장 느림). 최초 생성은 35~71초.
- 원인은 Muse Spark가 reasoning 모델이라는 점(`max_tokens` 8000 유지 필요)과 프롬프트(~4.6K자) 처리다. 네트워크·서버 처리(검증·저장)는 1초 미만.
- 현재 UX: 진행 상태 표시는 있으나 단순 요청("영상 섹션 숨겨 줘")도 같은 시간을 기다린다.

## 2. 제안: 규칙 우선(fast path)은 "좁고 정밀한" 범위에서만
규칙 해석기(`AssistantRuleInterpreter`)는 이미 있고 0.5~0.9초에 끝난다. 다만 **의도를 보존하지 못하는 요청이 있다**.

### 2.1 비교 (실측 코퍼스 중 설계 대상 23문장, 같은 판정 기준 = 서버 검증 통과 연산이 기대 조건을 만족)
| | 규칙 해석기 | Muse Spark(실측 25문장) |
|---|---|---|
| 의도 충족 | 18/23 (78%) | 24/25 (96%) |
| 되묻기/무연산(안전) | 3 | 1 |
| **의도와 다른 변경(위험)** | **2** | 0 |
| 시간 | 0.5~0.9초 | p50 ≈10초 |

위험 2건은 **문구 수정 요청이 디자인 변경으로 오해된 것**이다.
- "학원 소개 제목을 더 따뜻한 문장으로 바꿔 줘" → 규칙: 프리셋 전체를 WARM으로 변경(소개 제목은 그대로).
- "소개 문단을 조금 더 신뢰감 있게 다시 써 줘" → 규칙: 프리셋 EXAM으로 변경(문단은 그대로).
원인: 분위기 단어("따뜻", "신뢰")를 디자인 요청으로 보는 규칙이 문구 수정 동사("바꿔/다시 써")보다 앞선다. 그대로 fast path에 넣으면 **사용자의 의도와 다른 대규모 변경**이 나간다(되돌릴 수는 있으나 신뢰를 잃는다).
되묻기 3건(예: "카드를 둥글고 부드러운 느낌으로", "움직이는 효과는 다 꺼줘")은 안전하지만 규칙이 아직 못 푸는 것이라 AI로 보내면 된다.

### 2.2 fast path 적용 조건(안)
다음을 **모두** 만족할 때만 규칙 결과를 바로 적용한다. 하나라도 어기면 AI로 보낸다.
1. 요청에서 규칙이 만든 연산이 **고정밀 유형**뿐이다: 섹션 표시/숨김/이동, 명시적 색 이름+색 단어, 글꼴 이름, 상단 정렬 단어, 디자인 자산 키워드(`학교형·랜딩·서서히 등장` 등), 효과 끄기, 사진 삭제.
2. **의도 충돌 신호 없음**: 문구 수정어(`써 줘, 다듬, 문장, 문구, 제목을, 소개를, 카피`)가 없고, 분위기 단어(고급·따뜻·친근…)가 단독 요청이 아니다. 분위기 → 프리셋 복합 변경은 **항상 AI**.
3. **한 가지 의도**만 있다(복합 요청은 AI). 규칙이 연산을 하나도 못 만들면 AI.
4. 규칙이 만든 연산이 서버 검증을 전부 통과한다.

실측 코퍼스 기준 적용 대상은 13/25(52%: 섹션 3·색 2·글꼴 1·정렬 1·자산·효과 6)이며 모두 의도 충족이었다. 나머지 48%(분위기·문구·복합·규칙이 못 푸는 요청 — 예: "움직이는 효과는 다 꺼줘"는 현재 규칙이 못 알아듣고 되묻는다)는 계속 AI가 처리한다.
예상 효과: 해당 52%의 응답이 10초대 → 1초 미만. 전체 평균은 요청 구성에 따라 약 35~45% 단축(코퍼스 구성 기준 추정, 실제 비율은 그림자 모드로 확인)(AI가 쓰이는 요청은 그대로).

### 2.3 의도 보존 안전장치
- fast path 적용 결과도 지금처럼 변경 요약 + 되돌리기가 붙는다(요약에 "빠른 처리" 표시 없음, 동일 UX).
- **그림자 모드(shadow) 선행**: 처음에는 규칙 결과를 적용하지 않고 AI 결과만 쓰되, 같은 요청에 규칙 해석을 같이 돌려 로그(`agree/disagree`, 연산 차이)만 남긴다. 최소 100턴·불일치율 ≤ 2%·위험(의도 불일치) 0건을 확인한 뒤 fast path를 켠다.
- 기능 플래그(`buildit.assistant.fast-path`)로 즉시 끌 수 있게 한다(기본 OFF).
- 규칙 키워드를 늘릴 때는 같은 코퍼스에 "의도 충돌" 케이스(문구 수정+분위기 단어)를 반드시 추가해 회귀를 막는다(현재 2건을 회귀 테스트로 고정할 것).

## 3. 그 밖의 지연 개선 후보 (규칙 우선과 독립)
| 후보 | 기대 | 위험/비용 |
|---|---|---|
| 프롬프트 축소(허용 값 목록 압축·자산 목록은 관련 상위 N개만) | 입력 토큰 감소 → 소폭 단축 | 정확도 영향 → 코퍼스 재측정 필요 |
| Muse Spark 추론 강도/출력 길이 설정(API가 지원하면) | 복합 요청 단축 | 지원 여부 미확인, 정확도 재측정 |
| AI 호출 타임아웃(예: 30초) 후 안내 + 작업본 유지 | p95 꼬리 제한 | 느린 정상 응답을 잘라낼 수 있음 — 타임아웃은 측정 후 정함 |
| 최초 생성 분할(초안 먼저 → 문구 다듬기 후속) | 첫 화면 35~71초 → 수 초 | 생성 흐름 변경(별도 설계) |
| 진행 상태 문구 개선(현재 단계별 안내) | 체감 개선 | 실제 시간은 그대로 |

## 4. 측정·승인 기준
- 지표: 수정당 서버 처리시간(p50/p95), fast path 비율, 그림자 불일치율, 의도 불일치 신고(되돌리기 직후 재요청 비율), AI 폴백 비율.
- 승인 전 확인: ① 그림자 모드 결과 ② 코퍼스 25문장 + 의도 충돌 케이스 회귀 통과 ③ 플래그 OFF 시 현재 동작과 동일.
- 제외: 규칙으로 문구를 쓰는 것(규칙은 문구를 만들지 않는다 — 기존 원칙 유지).
