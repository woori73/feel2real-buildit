# Wiki TUTOR 브라우저 Context 조회·문제제작 원칙

> 적용 대상: Claude/MCP 등 에이전트가 학교별 내신 예상문제를 제작하면서 BuildIt Wiki 운영 자료를 Context로 사용하는 모든 작업

## 1. 최우선 원칙

학교별 Wiki Context가 MCP에서 비어 있다고 해서 **자료가 없다고 결론 내리지 않는다.** BuildIt Wiki의 학교별 업로드 자료는 TUTOR 권한이 필요한 운영 데이터일 수 있다. 사용자가 특정 학교·학년·학기·시험 자료가 이미 업로드되어 있다고 알려준 경우, 일반적인 출제 지식으로 우회하지 말고 실제 운영 Wiki 자료를 확인한다.

## 2. 문제 제작 전 필수 문서

작업 시작 전에 다음을 읽는다.

1. `CLAUDE.md`
2. `docs/INDEX.md`
3. `docs/exam/WIKI_TUTOR_BROWSER_CONTEXT.md` (이 문서)
4. `docs/exam/내신_시험지_제작원칙.md`

학교별 Wiki Context 기반 문제 제작에서는 이 문서와 내신 시험지 제작원칙을 함께 적용한다.

## 3. Wiki Context 조회 순서

1. BuildIt_Wiki MCP로 대상 학교 Context를 조회한다.
2. 정상적으로 자료가 반환되면 실제 내용을 읽는다.
3. MCP 결과가 empty이거나 사용자가 알려준 자료가 누락되면 데이터 부재로 단정하지 않는다.
4. 사용 가능한 브라우저/Computer Use 환경에서 실제 운영 Wiki를 연다.
5. **TUTOR 계정으로 로그인된 브라우저 세션**을 사용한다.
6. 대상 학교 → 학년 → 학기 → 시험 경로로 이동한다.
7. 목록/파일명만 확인하지 말고 실제 업로드 자료 내용을 읽는다.
8. 브라우저에서는 보이지만 MCP에서는 empty라면 `MCP 인증/권한 또는 TUTOR identity/session 전달 문제`로 기록한다.
9. 실제 자료를 확인한 뒤에만 학교별 예상문제 Blueprint와 문제 생성을 시작한다.

비밀번호, PAT, 세션 토큰 등 민감한 인증정보를 문서나 채팅에 기록하지 않는다.

## 4. 브라우저에서 우선 확인할 실제 자료

- 실제 중간/기말고사 기출 시험지
- 학교 프린트 원본
- 학교 프린트 필기본
- 교과서 본문 및 대화문
- Lesson별 자료
- Digital Twin
- Wiki Insight / 출제 분석
- 문항별 분석
- 기존 Question DB
- 기존 학교별 변형문제

자료 존재 여부만 보지 말고 다음을 추출한다.

- 정확한 시험범위와 Lesson
- 핵심 본문·대화문
- 핵심 어휘·영영풀이
- 핵심 문법
- 학교 프린트 강조사항
- 실제 기출 문제유형
- 선지 구성 방식
- 지문 변형 방식
- 객관식/서답형 비중
- 영작·서술형 특징
- 해당 학교의 반복 출제 패턴

## 5. Context Pack 1회 집중 분석

실제 자료를 확보하면 문제부터 만들지 않는다. 먼저 학교/학년/시험 단위의 `SCHOOL_CONTEXT_PACK`을 만든다.

Context Pack에는 최소한 다음을 포함한다.

- 학교 / 학년 / 학기 / 시험
- 시험범위
- Lesson별 핵심 내용
- 핵심 본문·대화문
- 중요 어휘
- 중요 문법
- 학교 프린트 강조사항
- 실제 기출 유형
- Digital Twin 패턴
- Wiki Insight
- 유형별 출제 빈도와 난이도 특징
- 서답형 특징
- 원자료 provenance

문제를 여러 단계로 나누어 생성하더라도 전체 Wiki 자료를 단계마다 처음부터 반복 분석하지 않는다. 동일 Context Pack을 재사용하고, 근거가 불확실한 특정 항목만 원자료에서 선택적으로 재확인한다.

## 6. 대량 문항 분할 생성 규칙

대량 문항은 한 번에 전부 생성하지 않는다. **Context 분석과 전체 Blueprint는 처음 한 번만 만들고**, 실제 문제 생성만 20문항 안팎의 batch로 분할한다.

기본 분할:

- **40문항:** `Q1~20 → Q21~40`
- **70문항:** `Q1~20 → Q21~40 → Q41~60 → Q61~70`
- **100문항:** `Q1~20 → Q21~40 → Q41~60 → Q61~80 → Q81~100`

문항 수가 위 기준과 다르면 원칙적으로 20문항 단위로 나누고 마지막 batch에 나머지를 배치한다. 단, 실제 문제의 길이·서답형 비중·Context 복잡도가 높으면 한 batch를 더 작게 나눌 수 있다.

### 6.1 전체 Blueprint 우선

각 batch를 독립적으로 설계하지 않는다. 예를 들어 70문항이면 **Q1~70 전체 Blueprint를 먼저 확정**한다. Blueprint에는 최소한 문항번호, 객관식/서답형, 문제유형, Lesson/범위, 출제근거, 핵심 평가요소, 난이도, 예상 정답 형태를 기록한다.

이렇게 해야 뒤 batch에서 앞 batch와 동일한 본문·문법·발문을 반복하는 것을 줄일 수 있다.

### 6.2 batch별 생성·즉시 검증

각 batch는 `생성 → 독립 정답 검증 → 오류 수정 → batch 완료` 순서로 처리한다. 현재 batch의 검증이 끝나기 전에 다음 batch로 넘어가지 않는다.

70문항 예시:

`Context Pack → Q1~70 Blueprint → Q1~20 생성/검증 → Q21~40 생성/검증 → Q41~60 생성/검증 → Q61~70 생성/검증`

100문항도 같은 방식으로 20문항씩 진행한다.

### 6.3 이전 문항 전체 재주입 금지

뒤 batch를 만들 때 앞에서 완성한 HTML/해설 전체를 매번 Context에 다시 넣지 않는다. 대신 다음과 같은 **압축 상태표**를 유지한다.

- 이미 사용한 본문/대화문
- 이미 사용한 핵심 어휘/문법
- 이미 사용한 문제유형과 횟수
- Lesson별 누적 문항 수
- 난이도 분포
- 객관식/서답형 누적 수
- 정답 번호 분포
- 중복 방지를 위한 문항 요약
- REVIEW 문항 목록

뒤 batch는 `SCHOOL_CONTEXT_PACK + 전체 Blueprint + 압축 상태표`를 기준으로 생성한다. 특정 근거가 필요할 때만 원자료를 선택적으로 다시 읽는다.

### 6.4 대량 문항 Cross Validation

모든 batch가 끝난 후 전체를 한 번에 장문 재생성하지 않는다. 먼저 범위를 나눠 상세 검증하고, 마지막에는 전체에서 중복·편중·정답분포·범위 누락을 Cross Check한다.

권장:

- **40문항:** Q1~20 상세검증 + Q21~40 상세검증 → Q1~40 전체 Cross Check
- **70문항:** Q1~35 상세검증 + Q36~70 상세검증 → Q1~70 전체 Cross Check
- **100문항:** Q1~25 / Q26~50 / Q51~75 / Q76~100 상세검증 → Q1~100 전체 Cross Check

전체 Cross Check에서는 문제와 해설을 불필요하게 다시 생성하지 말고 다음을 집중 확인한다.

- 사실상 동일한 중복문항
- 특정 Lesson/본문 편중
- 특정 문법/어휘 반복
- 문제유형 편중
- 난이도 편중
- 객관식 정답 번호 편중
- 문항번호/선택지/정답 밀림
- `(A)(B)(C)` 개수 불일치
- `①~⑤` 본문 표시 불일치
- 밑줄/빈칸 누락
- 복수정답 가능성
- 시험범위 밖 문항

### 6.5 토큰 효율보다 정확성 우선

Context Pack 재사용과 압축 상태표는 불필요한 반복 토큰을 줄이기 위한 것이지만, 정확성 검증에 필요한 원자료 재조회까지 금지하는 것은 아니다. 근거가 불확실하면 해당 원자료를 다시 확인한다.

**토큰 절약을 이유로 Context 근거 확인이나 정답 검증을 생략하지 않는다.**

## 7. 권장 문제 제작 흐름

`필수 docs 확인 → MCP 조회 → 필요 시 TUTOR 브라우저 조회 → 실제 자료 읽기 → SCHOOL_CONTEXT_PACK 고정 → 전체 문항 Blueprint → 20문항 안팎 batch 분할 생성 → 각 batch 독립 검증 → 전체 Cross Validation → A4 조판 → DB 등록용 검증 데이터`

## 8. 문제 품질 및 정답 검증

문제를 생성할 때 예상한 정답을 그대로 신뢰하지 않는다. 각 문항 완성 후 다시 독립적으로 풀어 정답을 검증한다.

구조화 데이터에서는 최소한 다음을 분리한다.

- `createdAnswer`: 생성 시 예상한 정답
- `verifiedAnswer`: 독립 재검증으로 확정한 정답
- `validationStatus`: `VERIFIED` 또는 `REVIEW`

`createdAnswer != verifiedAnswer`이면 자동 통과시키지 않고 원문과 Context를 재확인한다. 복수 정답 가능성, 발문/본문 불일치, 서답형 조건 충돌, 근거 불확실성이 있으면 `REVIEW`로 남긴다.

## 9. Question DB 등록 대비 원칙

문제와 정답은 하나의 Question record 단위로 유지한다. 문제번호 순서에만 의존하는 별도 positional answer array로 매칭하지 않는다.

각 문항에는 가능한 범위에서 다음을 함께 유지한다.

- questionNumber
- questionType
- prompt
- passage
- choices
- createdAnswer
- verifiedAnswer
- explanation
- lesson
- source
- provenance
- validationStatus

문항 재정렬·삭제·수정이 발생해도 정답이 다른 문제로 밀리지 않아야 한다. `REVIEW` 문항은 READY로 간주하거나 자동 등록하지 않는다. 실제 DB 등록 작업에서는 저장 후 DB를 다시 읽어 문제·선택지·정답 매칭을 재검증한다.

## 10. 내신 시험지 조판 연결

Context 기반 문제 생성이 끝나면 `docs/exam/내신_시험지_제작원칙.md` 전체를 적용한다. 특히 다음 핵심 계약을 지킨다.

- 문제 번호 옆 점수 금지, 번호 바로 뒤 발문
- 제작자 `압구정에듀홀릭 내신 wiki`
- 짧은 단어형 선택지는 가로 배열 우선
- A4 210×297mm 페이지를 먼저 구성
- 각 A4 내부 왼쪽/오른쪽 2단
- 실제 렌더링 문항 높이 기준 `왼쪽 → 오른쪽 → 다음 A4` 배치
- 문항 수 기준 강제 좌우 분할 금지
- CSS `column-count`만으로 핵심 조판 금지
- 발문·지문·선택지 문항 블록 분리 금지
- 섹션 제목 고립 금지
- 빈 마지막 페이지 금지
- 화면과 인쇄에서 동일한 핵심 A4 DOM 구조 사용
- 약 9~10pt 수준의 가독성 유지
- 서답형 실제 작성 공간 확보
- 학생용 시험지에 정답·해설·AI 제작과정·Digital Twin 근거 노출 금지

핵심: **A4를 먼저 만들고, 실제 문항 높이를 측정해서 좌 → 우 → 다음 페이지로 흘린다.**

## 11. 금지 사항

- MCP `empty`만으로 `Wiki Context 없음` 결론
- 실제 운영 자료 확인 전에 일반적인 학교 출제 관행으로 특정 학교 문제 제작
- 인증 문제를 데이터 부재로 오인
- 사용자에게 GitHub PAT, 비밀번호, 세션 토큰 등 민감정보를 채팅으로 요구
- 파일명/목록만 보고 실제 내용을 읽지 않은 채 Context 분석 완료 처리
- Context에 없는 Digital Twin/학교 출제경향을 추측해 생성
- 생성 당시 정답을 독립 검증 없이 DB 정답으로 확정
- REVIEW 문항을 억지로 VERIFIED 처리
- 40/70/100문항을 한 번에 생성하여 뒤쪽 문항의 중복·품질 저하를 방치
- batch마다 Wiki 전체 Context를 처음부터 반복 분석

## 12. 브라우저 사용이 불가능한 환경

현재 에이전트 세션에 브라우저/Computer Use 기능이 없다면 가능한 것처럼 가장하지 않는다.

- MCP가 정상 조회되면 MCP 자료로 진행한다.
- MCP가 empty이고 브라우저 접근도 불가능하면 실제 학교 자료를 확인하지 못했다고 명시한다.
- 이 상태에서 특정 학교 Digital Twin 기반 예상문제를 임의 생성하지 않는다.
- 사용자가 자료를 직접 첨부하도록 요청하거나 브라우저 사용이 가능한 실행 환경으로 작업을 넘긴다.

## 14. 최종 판단 원칙

**특정 학교 예상문제의 품질은 일반적인 영어 문제 생성 능력보다 실제 학교 Context의 정확한 확인과 provenance 추적을 우선한다.**

MCP와 TUTOR 브라우저가 서로 다른 결과를 보이면 실제 운영 TUTOR 세션에서 확인되는 자료를 기준으로 원인을 구분하고, 자료가 확인되기 전에는 학교별 출제경향을 추측해서 채우지 않는다.

## 15. 실제 기출 원본 PAST_EXAM 계약 + AI 작업기록 AI_WORK_LOG

학교별 Context의 `PAST_EXAM`은 AI 예상문제나 Digital Twin이 아니라 실제 학교에서 시행된 PDF/HWP/HWPX/HTML/HTM/MD/MARKDOWN/JPG/JPEG/PNG 시험지 원본 증거다. Context/MCP는 학교·학년·학기·시험·시험연도·업로더·업로드시각·원본 접근 식별자를 provenance와 함께 노출한다. HTML/MD로 올린 기출은 `body_text`를 함께 실어 1번·10번 실제 발문, 서답형 작성요령 같은 문면을 metadata가 아니라 원문으로 읽을 수 있다. HTML은 script/style/편집기 toolbar·화면전용 UI를 제거하고 제목·문항·지문·선택지·표·보기·밑줄/강조·서답형 작성요령만 남긴 정제본이다(원본 파일은 `/original`로 그대로 보존). `body_format`이 `html`|`markdown`이고, 각 항목에 `body_included`/`body_truncated`/`body_length`/`body_chars`가 붙는다. `past_exams`+`ai_work_logs` 본문은 항목당 200,000자·합산 600,000자로 제한되며, budget 때문에 잘리거나 빠진 자료는 응답 `context_budget.truncated_items`/`omitted_items`로 명시되므로(조용히 빠지지 않는다) 필요하면 해당 자료의 `body_api_path`/`original_api_path`로 다시 연다. PDF·이미지·HWP(X) 기출은 여전히 원본 접근 식별자만 노출한다.

`AI_WORK_LOG`는 Claude/ChatGPT가 이 시험 준비 과정에서 남긴 작업 로그(MD/MARKDOWN/TXT/HTML)다. FINAL Context의 `ai_work_logs`로 본문이 그대로 전달되어, 다음 세션에서 이전 분석·할 일을 이어받는다. 자동 분석과 Digital Twin 자동 갱신은 별도 후속 범위다.
