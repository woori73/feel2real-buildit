### 2-1. DB 트랜잭션 실패 시 미연결 파일 — 영향 평가 (실측)

실측: 30번째 컷 저장에서 DB 실패를 주입 → **DB는 전부 롤백**(`studio_files` 71→71, `studio_revisions` 70→70)되지만 **저장소 객체는 71→101(고아 30개)**. 같은 입력으로 재시도하면 성공하나 롤백된 파일은 SHA 중복 검사에 걸리지 않아 객체가 68개 더 늘고(101→169), 최종 **참조 139 / 전체 169 = 고아 30개가 영구 잔류**.

| 영향 | 평가 |
|---|---|
| 데이터 무결성 | 없음. DB에 끊긴 참조 없음, 기존 원본·승인 이력 변화 없음(실측) |
| 노출 | 낮음. 고아 객체는 DB 행이 없어 API로 접근 불가(파일 ID 필요). 단 저장소에는 사용자가 "롤백"으로 여긴 내용이 남음(보존 정책 이슈) |
| 비용 | 실패 1회당 최대 ~67개 객체, 해제 합계 20 MiB 상한 → **실패 1회당 ≤ 20 MiB**. 트리거는 DB 오류·동시 head 변경(409)·시간 초과로, EDITOR가 의도적으로 반복할 수도 있고 일괄 등록에 속도 제한은 없음 |
| 사용성 | 재시도는 정상 동작 |
| 판정 | **P2** (병합 차단은 아니나 운영 전 수정 권장) |

**수정 방안 (Codex 구현, 기존 파일·이력 삭제 없음)**
1. `StudioService.upload`가 `saveRaw` 직후 **롤백 시 방금 만든 키만 삭제**하도록 등록: 저장소에 이미 `TransactionalFileDeletion.onReplace(()->{}, ()->storage.delete(key,type))` 선례가 있음(위키 서비스). 새 UUID 키만 대상이라 기존 객체는 건드리지 않음. 수용 기준: `IndependentStudioProbeMySqlTest.failureMidImportRollsBackDbButLeavesUnlinkedFiles`의 `orphans > 0` 단언을 `== 0`으로 바꿔 통과.
2. 안전망(선택): `studio-` 접두 객체 중 `studio_files.storage_key`에 없고 24시간 이상 지난 것만 **먼저 보고서(dry-run)로 출력**하고 승인 후 삭제하는 점검 스크립트. 참조 객체 삭제 금지를 테스트로 보장.
3. 운영 점검 쿼리: 저장소 목록과 `studio_files.storage_key`의 차집합 개수 확인.
영향 범위: `StudioService.upload` 1곳 + 테스트, 스키마 변경 없음, 기존 데이터 영향 없음.
