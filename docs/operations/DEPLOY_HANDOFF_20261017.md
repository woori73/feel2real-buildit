## 5. 신규 AWS 이전 계획 (기존 계정은 사용자가 인수·접근 가능, 외부 협조 불필요)
**조사 결과(2026-10-17)**
- 이 세션(클로드)의 AWS 자격 증명은 STS가 `InvalidClientTokenId`로 거부 → **현재 EC2·RDS·S3·Route53·KMS 접근 가능 여부는 확인하지 못했다.** 사용자가 읽기 전용 자격 증명을 환경 시크릿(변수명 지정)으로 넣어 주면 아래 확인 항목을 읽기 전용으로 점검한다. 키를 채팅에 붙여 넣지 않는다.
- 저장소에서 확인된 구조: 리전 `ap-northeast-2`, 구 계정 OIDC 배포 역할 `github-actions-f2r-deploy`, 배포 버킷 `feel2real-buildit-deploy`, 배포는 S3 업로드 + SSM `send-command`, ALB 유휴 180초 이상 필요, 도메인 `feel2real.co.kr` + `*.feel2real.co.kr`(학원별 서브도메인) → **와일드카드 인증서·DNS가 전환의 핵심**.

**읽기 전용 확인 항목(자격 증명 확보 후)**
1. 권한: EC2·RDS·S3·Route53·KMS·ACM·SSM·IAM 읽기(`Describe*/List*/Get*`)
2. RDS: 엔진/버전, 암호화 여부와 KMS 키(AWS 관리형 `aws/rds` 키 스냅샷은 **다른 계정과 공유 불가** → 고객 관리형 CMK로 복사 후 공유 필요), 자동 백업, 파라미터 그룹, 서브넷/SG
3. KMS: 키 정책에서 신규 계정 사용 허용 가능 여부(키 소유자 권한 필요)
4. S3: 버킷별 용량·객체 수·암호화(SSE-S3/KMS)·버전·수명주기·CORS, 신규 계정으로의 복사 경로(버킷 정책 교차 계정 읽기 또는 구 계정 자격으로 `s3 sync`)
5. DNS: Route53 호스팅 영역 보유 여부와 가비아 네임서버 위임 상태(어느 쪽이 권한 서버인지), 현재 TTL, 와일드카드 레코드·ACM 검증 레코드
6. 구 계정 EC2: 인스턴스 프로파일·SG·ALB 리스너/인증서, 환경 파일 항목 목록(값 제외)

**실행 계획(각 단계 사용자 승인 필요 표시 ★)**
1. 뮤즈: 신규 VPC·EC2·ALB·S3 구축 → 클로드에게 인계(설정 문서 포함)
2. 클로드: 신규 환경 검증(보안그룹·IAM·OIDC — §6 기준), 구 환경 변경 없음
3. ★ 구 계정 RDS 스냅샷 생성(필요 시 CMK로 복사·공유) → 신규 계정으로 복원(공유 또는 복사)
4. 클로드: 복원본에서 정합성 검증(행 수·체크섬·Flyway 이력 V1085) → V1086·V1087 리허설
5. ★ S3 데이터 복사(`sync`, 복사 후 객체 수·크기 대조). 구 버킷은 그대로 유지
6. 신규 환경에 같은 SHA 배포(스테이징 URL), 전체 스모크(로그인·업로드·AI 기능 비활성 상태 포함)
7. ★ 컷오버 창: 쓰기 정지 안내 → 최종 증분(스냅샷 재생성/복원) → DNS 전환(TTL 사전 인하, 가비아/Route53 중 권한 서버 한 곳만 수정, 와일드카드 포함) → 모니터링
8. 롤백: DNS를 구 ALB로 되돌림(구 환경·RDS는 안정 확인 전까지 유지·중지 금지). 컷오버 이후 신규 DB에 쌓인 쓰기는 롤백 시 손실되므로 컷오버 직전 쓰기 정지 시간을 짧게 두고 롤백 기한을 정한다
9. ★ 안정 확인(예: 7일) 후 구 환경 정리 여부는 별도 승인

## 6. 뮤즈 IAM·OIDC·워크플로 보안 검토 (산출물 미수령 → 승인 보류)
IAM 정책 JSON·GitHub Actions YAML이 저장소·브랜치에 없어 **검토를 시작하지 못했다. 뮤즈가 두 파일(비밀 제외)을 전달하면 아래 기준으로 검토하고 승인 의견을 낸다.** 현재 승인 의견: **보류(내용 미확인)**.
- 신뢰 정책: `aud=sts.amazonaws.com`, `sub`를 저장소+브랜치/환경으로 정확히 고정(`repo:woori73/feel2real-buildit:ref:refs/heads/main` 또는 `environment:` 단위, 와일드카드 금지). `job_workflow_ref`는 IAM 신뢰 정책 조건 키로 직접 쓸 수 없는 경우가 있으므로(지원 여부를 정책 변수 목록에서 확인) 불가하면 **GitHub Environment 보호 규칙 + `sub`(environment) 고정 + 필수 리뷰어**로 대체. 포크 PR·다른 브랜치·`workflow_dispatch` 임의 ref가 역할을 가정하지 못해야 한다
- 권한 확대 위험: 워크플로 파일을 수정하는 PR이 같은 역할을 쓸 수 있으면 권한 확대 가능 → 배포 역할은 main·보호된 Environment에서만, `pull_request` 트리거에는 읽기 전용 별도 역할
- 정책: `Action/Resource` 와일드카드·`iam:PassRole`·`iam:*`·`s3:*`·`ssm:SendCommand` 무제한 금지. SSM은 **대상 인스턴스 태그/ARN + 특정 문서만**, 명령 본문은 고정 스크립트
- 네트워크: RDS는 비공개 서브넷·퍼블릭 접근 off·SG는 EC2 SG에서만 3306, EC2는 ALB SG에서만 앱 포트, SSH 미개방(SSM Session), ALB는 443만(80→443 리다이렉트), S3 퍼블릭 차단·버킷 정책 TLS 강제
- 중복 실행·부분 실패: 배포 워크플로 `concurrency` 그룹(중복 방지), 인프라 생성은 멱등(IaC 상태 잠금), 실패 시 비용이 계속되는 리소스(NAT·ALB·RDS·EIP) 정리 절차, Budgets 알림(월 $90) 임계 단계별
- 비용·크레딧: 월 구성(EC2·RDS·ALB·NAT·S3·데이터 전송) 항목별 추정치 제출 요구, 크레딧 소진 시점
- 격리: 신규 계정에 구 계정 리소스 접근 권한이 남지 않게(구 계정 키를 신규 시크릿에 저장 금지), 교차 계정 접근은 이전 기간 한정·읽기 전용·종료 후 회수
