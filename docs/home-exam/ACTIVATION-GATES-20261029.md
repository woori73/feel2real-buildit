# 신청 활성화 경계·개인정보 보완 — 운영 미적용

기준 main `fb17c25d`(#919·#920). 별도 브랜치에서 준비했다. 운영 DB/JAR/미디어 변경, 배포, 유료 API, 실제 입금/환불은 실행하지 않는다.

## 계좌와 접수 분리

| 설정 | 기본값 | 효과 |
|---|---|---|
| `app.exam-intake.bank-admin-enabled` | false | ADMIN 전용 `/admin/hub/exam-bank`와 기존 관리자 계좌 API |
| `app.exam-intake.enabled` | false | 고객 접수·파일·관리자 접수 처리 |
| `app.exam-intake.bank-public-enabled` | false | 접수 활성 + 승인 계좌가 있을 때만 고객 계좌 노출/입금 확인 요청 |

계좌 서비스는 파일 저장소나 신청 테이블 초기화에 의존하지 않는다. 운영 스키마가 없으면 기동은 유지하고 관리자 조회에 상세 SQL/계좌값 없는503을 응답한다. 스키마 설치 승인을 대신하지 않는다. 계좌 저장은 승인을 해제하며 별도 승인/버전/감사 로직을 재사용한다. 공개 OFF 또는 승인 해제 시 과거 입금 요청의 계좌 스냅샷도 고객 상세에서 가린다. 관리자 감사 자료는 보존한다.

## 동의·연령과 법정대리인 확인

`/exam-service/privacy`, `/exam-service/terms`는 개인정보 없는 안내 페이지로 신청 비활성 상태에서도 읽을 수 있다. 기존 NewStart `/privacy`는 보존한다. 개인정보 필수 동의, 선택 정보 동의, 신청의 이용·환불 약관 동의는 분리하며 미리 체크하지 않는다. 연령은 `OVER14`/`UNDER14`만 저장하고 생년월일·주민번호를 추가 수집하지 않는다.

사용자가 승인한 방식: 성인 법정대리인이 자신의 계정에서 이름·전화·관계와 전자동의를 먼저 제출 → ADMIN이 전화로 신원·법정대리 권한 및 동의 내용을 설명하고 동의 의사 확인 → 같은 계정의 한 건 신청 허용. 실제 전화는 담당자가 수행하며 프로그램의 체크박스가 신원 확인을 대신하지 않는다.

추가 제안 테이블 `exam_intake_guardian_consent`에 성인 정보, 동의 항목/정책 버전/시각, 확인자/방법/시각/결과, 사용한 신청, 철회 이력을 기록한다. 아동 정보는 확인 요청에 저장하지 않는다. `PENDING → VERIFIED → USED`, `REJECTED`(거절/확인 불가), `REVOKED`를 구분한다. 미사용 확인은30일 유효하며 타인/만료/구버전/철회/재사용을 거부한다. 사용자에게는 자기 요청만 보이며 ADMIN만 전화 확인/거절할 수 있다. 수정은 철회 후 새 요청으로 처리하고 감사 이력을 임의 삭제하지 않는다.

새 신청의 정책 버전은 `exam-intake-review-20261029-v3`, 개인정보 `exam-privacy-20261029-v1`, 약관 `exam-terms-20261029-v1`. 서버에서 별도 동의를 검사하고 기존 payload에 보존한다. 관리자 내용 수정으로 연령/동의 버전·항목을 위조하거나 과거 계약에 새로운 동의를 소급 삽입하지 않는다. 파일 업로드는 선택 제출 동의를 받으며, 보안 필터에서 소유권·동의 상태를 multipart 본문 파싱 전에 확인한다.

## 보존·삭제

정책 준비안: 일반 문의·신청·학습자료는 종결/종료/취소 후 최대30일 이내 정리. 불필요한 정보나 유효한 삭제 요청은 더 일찍 처리 가능하다. 미입금 중단 건은 담당자가 종결 판단 후 처리한다. 법정 기록은 계약/청약철회 및 결제/공급5년, 분쟁3년, 광고6개월을 구분한다. 학습자료 전체를 거래기록으로 간주하지 않는다. 백업 최대35일 순환안은 실제 인프라 검증·승인이 필요하다.

ADMIN의 만료 대상 조회와 수동 학습자료 삭제를 구현했다. `app.exam-intake.retention-reviewed-policy-version` 기본 빈 값으로 실제 삭제를 차단한다. 법적 검토된 버전이 개인정보 버전과 일치하고, 종료/취소·목적 달성·법적 보존 유보 없음이 확인되어야 실행한다. 진행 중인 수정/취소/환불/개인정보 요청은 먼저 처리해야 한다. 30일은 보관 상한이며 삭제 요청에 최소 보관 기간으로 강제하지 않는다.

파일은 먼저 비공개 처리하고 삭제 실패 시 `PRIVACY_ERASURE/PROCESSING`으로 남긴다. 실패를 성공으로 표시하지 않고 재시도할 수 있다. 완료 후 신청 본문·학습 변경 이력·파일명·보호자 연락정보를 정리한다. 결제/계약의 최소 증빙·회차·처리 시각은 보존한다. 미사용 보호자 연락정보도 만료·거절·철회 시 ADMIN이 정리한다. 자동 스케줄러나 운영 삭제는 실행하지 않았다.

열람·정정·삭제·처리정지 요청은 `PRIVACY_REQUEST`로 접수하며 취소 완료 후에도 허용한다. 법정 보존 사유/이의 처리, 백업 삭제와 복원 후 재삭제, 법정 기간이 지난 금융 증빙 파기는 운영 담당자의 별도 절차가 필요하다. 자동으로 기존 금융기록을 삭제하지 않는다. 삭제 담당자·일일 점검·접속기록 보존과 실제 백업 만료를 확정하기 전 운영 활성화하지 않는다.

## 환불·사업자

2주·4회·40문항·160문항·20,000원 보존. 0~4회 기본 예정액20,000/15,000/10,000/5,000/0원은 기존 계산을 재사용한다. 법정 청약철회·미제공·사업자 귀책/하자가 우선하며 일반 약관 동의를 철회권 포기로 취급하지 않는다. 자동 확정/송금 없음. 기존 `refund-reviewed-policy-version` 승인 장치는 유지한다.

출판사 사업자 데이터와 주소 및 `exam-seller-confirmed` 기본값을 변경하지 않았다. 신고증 원본/현재 등록 주소를 읽을 연결이 없어 실제 대조는 미검증이다. 임의 새 주소를 추가하지 않는다.

## 법령 대조와 운영 한계

- [개인정보 보호법 제15조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1029334879): 동의 목적/항목/기간/거부권 고지.
- [제21조](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1006183947): 목적 달성·기간 경과 시 파기 및 법적 보존 분리.
- [시행령 제17조의2](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=02&joNo=0017&lsiSeq=289537&urlMode=lsScJoRltInfoR): 전화로 동의 내용을 알리고 동의를 받는 방법 등. 체크 하나만으로 확인 완료 처리하지 않는다.
- [전자상거래법 제17~18조](https://law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029561303), [거래기록 보존](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lspttninfSeq=63460): 가분적 미제공분·철회 기산점·하자·환급 기한/보존 기간을 구분.

법령 원문 대조는 최종 법률 적합성 승인과 다르다. 책임자 지정·위탁/국외이전·보존/백업 운영안, 현재 주소, 실제 검사기와 알림 수신은 별도 확인한다. AWS 실행 identity/운영 브라우저 연결 없음. 운영 계좌/파일 권한/백업/캐시/성능/실제 수신/전화 확인은 미검증으로 남긴다.

## 검증

기존 CI 증거는 재사용하고 변경 범위에 H2/JDBC·실제 Spring/MySQL E2E를 추가했다. 계좌 OFF/신청 OFF는 별도 서버 포트8092/8093에서 테스트한다. 합성 데이터만 사용하며 테스트 SMTP/검사기 대역은 실제 운영 성공으로 보고하지 않는다. 최초 다중 서버 준비에서 ApplicationReady seed의 동시 삽입이 충돌하여, CI는 초기 seed 트랜잭션 커밋 후 추가 서버를 시작하도록 조정했다. 해당 테스트 환경 문제를 운영 코드 수정으로 처리하지 않았다.

실제 MySQL E2E에서 법정대리인 접수의 기존 사용자 키를 `id`로 잘못 참조한 결함을 확인하여 실제 스키마의 `users.user_id`로 수정했다. H2 사용자 테이블도 같은 키를 사용하도록 교정했다. 권한 검사 E2E의 필수 boolean 누락과 Playwright의 fieldset disabled 판정 대상도 수정했다. 최종 검사는 fieldset 속성뿐 아니라 실제 이름 입력과 제출 버튼의 비활성 여부를 확인한다. 최종 실행 수·CI URL은 PR 및 작업 보고서에 기록한다.

## 운영 적용 전

1. 정책·실제 전화 확인 지침과 담당자, 현재 주소, 저장소/검사기/알림/보존 절차를 확정한다.
2. 실제 Flyway 이력과 정상 JAR/미디어 해시, 독립 백업·복구 권한 확인 후 신규8개 테이블의 마이그레이션을 별도 승인한다. 이 PR은 `db/migration`을 변경하지 않는다.
3. 승인된 코드 배포 후 고객 신청/계좌 공개 OFF를 유지하고, 별도 승인된 관리자 사전 등록만 켠다. 지정 계좌 저장·승인 상태를 확인한다.
4. 격리 검증 및 운영 필수 항목 PASS 후 별도 활성화 승인으로 신청과 고객 계좌 공개를 켠다. 삭제 정책 설정은 검토 완료 후에만 등록한다.
5. 장애 시 접수·계좌 공개를 끄고 검증된 직전 JAR로 복구한다. 신규 신청/감사/동의 기록을 삭제하거나 DB 전체를 과거 상태로 덮어쓰지 않는다.
