# BuildIt 통합 대화형 화면 설계 (공통 UI 킷 확장 조건 포함)

- 상태: **설계안 (구현 전).** 구현은 단계별 승인 후 진행한다.
- 기준일: 2026-10-12
- 근거: Lovable 실제 화면 캡처(시작 화면, 템플릿 목록, 대화 화면)와 BuildIt 기존 코드 조사
- 원칙: Lovable의 **구조와 동선만 참고**한다. 로고·아이콘·그라데이션·문구 등 브랜드 고유 요소와 자산은 복제하지 않는다.

## 1. 목표와 범위

### 1.1 BuildIt 목표
사용자는 하나의 대화 화면에서 AI 홈페이지를 **제작·수정·게시**한다. 별도 빌더·편집기 화면을 서비스처럼 노출하지 않고, 기존 엔진(AI 생성, Muse Spark, 디자인 프리셋 10종, 시각 편집기, 저장·게시)을 내부에서 재사용한다.

### 1.2 장기 확장 조건 (이번에 추가)
이 대화형 UI는 이후 아래 세 서비스에 공통 적용한다.

| 서비스 | 용도 | 향후 외부 실행 작업 |
|---|---|---|
| BuildIt | AI 홈페이지 제작·수정·게시 | 공개 홈페이지 게시 |
| NewStart 지피지기 | 운영 DB/RAG 상담 | 금감원 민원 제출, 새출발기금 신청(Playwright 기반 지원) |
| 이지장부 | 증빙 업로드 → AI 거래 분석 → 복식부기 장부 작성 | 사업장현황신고, 종합소득세 신고 지원 |

**공통 UI만 공유하고, 각 서비스의 AI 엔진·DB·권한·업무 규칙은 독립적으로 유지한다.**

### 1.3 이번 설계가 하지 않는 것
- BuildIt 1단계(작업본 저장소·게시 API·비공개 미리보기) 구현 범위는 **확대하지 않는다.** 이 문서의 공통 UI 항목은 2단계 이후의 인터페이스와 확장 지점만 정의한다.
- NewStart와 이지장부의 실제 기능 구현은 별도 단계·별도 승인이다.

## 2. 사용자 화면 구성 (BuildIt)

| 화면 | 내용 |
|---|---|
| A. 시작 | 입력 카드 하나 + 디자인 샘플 4~6개. 시작 방법: 샘플 선택, 자연어 설명, 자료 첨부 |
| B. 대화 | 한 줄 대화(최대 폭 약 735~760px). 필요한 것만 묻는 선택 카드, 진행 표시, 결과 미리보기 카드 |
| C. 전체 화면 미리보기 | 카드 클릭 시 실제 홈페이지 전체 화면. `대화로 돌아가기`, 화면 크기 전환, `직접 편집`, `게시` |
| D. 직접 편집(고급) | 기존 시각 편집기. 일반 사용자 화면에는 숨기고 필요할 때만 접근 |

대화에서 만든 결과는 **작업본**에만 쓰이고, `게시` 때에만 공개 홈페이지에 반영된다.

## 3. 공통 UI 컴포넌트 (재사용 단위)

UI 킷은 **표현과 상호작용만** 담당한다. 데이터·업무 규칙·권한은 서비스 어댑터가 맡는다.

| 컴포넌트 | 역할 | 서비스가 주입하는 것 |
|---|---|---|
| ChatShell | 메시지 목록, 스트리밍 표시, 중단, 스크롤 | 메시지 데이터 소스 |
| Composer | 입력창, 모드 선택, 첨부 버튼, 음성 입력 | 모드 목록, 안내 문구 |
| AttachmentTray | 첨부 슬롯, 업로드 상태, 오류 표시 | 허용 형식·크기·개수 정책, 업로드 처리 |
| TaskProgress | 작업 단계 목록, 상태(대기/진행/완료/실패), 취소 | 단계 이름과 상태 이벤트 |
| ResultCard | 결과 요약 카드. 종류별 렌더러를 등록해 확장 | 카드 종류(kind)별 렌더러 |
| PreviewSurface | 카드 → 전체 화면 → 대화로 복귀. 크기 전환 | 미리보기 내용 렌더러(홈페이지, 장부 표, 서류 등) |
| ApprovalPrompt | 실행 전 요약·영향·되돌림 가능 여부 표시, 승인/거절 | 승인 대상 요약, 위험 등급 |
| ActivityLog | 작업 기록 타임라인, 되돌리기 링크 | 기록 데이터, 되돌리기 동작 |
| (공통) 테마 토큰 | 색·폰트·모서리를 변수로 분리해 서비스별 브랜드 적용 | 서비스 테마 값 |

구현 방식은 기존 스택(Thymeleaf SSR + 정적 JS)과 일관되게 **프레임워크를 새로 도입하지 않고**, 정적 JS 모듈(또는 커스텀 엘리먼트)과 CSS로 만든다. 서비스별 로직은 킷 안에 넣지 않는다.

## 4. 서비스 어댑터 계약 (확장 지점)

킷은 `ServiceAdapter` 하나만 안다. 각 서비스는 자기 API를 이 형태로 감싸서 제공한다.

```text
ServiceAdapter
  id: "buildit" | "newstart" | "easyledger" | ...
  capabilities: { attachments, approval, preview, history }
  attachmentPolicy(): { types[], maxBytes, maxFiles }
  send(input, attachments, context) -> 이벤트 스트림
  cancel(taskId)
  decide(actionId, decision, approvalToken)   // 승인/거절
  history(cursor) -> 작업 기록
  renderers: { [cardKind]: Renderer, previewKinds... }
```

서버 → UI 이벤트(공통 형식):

| 이벤트 | 의미 | 주요 필드 |
|---|---|---|
| `message` | AI/시스템 문장 | text, role |
| `question` | 선택 카드(예: 분위기 선택) | options[], allowFreeText, skippable |
| `progress` | 작업 진행 | taskId, steps[], state |
| `result` | 결과 카드 | kind, summary, payload, previewRef |
| `approval_request` | 사용자 승인 필요 | actionId, summary, risk, reversible, expiresAt, summaryHash |
| `error` | 오류 | code, message, retryable |
| `done` | 턴 종료 | taskId |

각 서비스 서버는 **자기 네임스페이스의 API**로 이 이벤트를 만들고, 서로의 DB·권한·규칙에 접근하지 않는다.

## 5. 서비스별 매핑

| 항목 | BuildIt | NewStart 지피지기 | 이지장부 |
|---|---|---|---|
| 입력/첨부 | 글, 로고·사진, PDF, Word | 질문, 서류 사본 | 영수증·계좌·카드 내역(이미지, PDF, 엑셀) |
| 엔진 | Muse Spark / 프리셋 | 기존 RAG·LLM 경로 | 거래 분석·복식부기 규칙 |
| 결과 카드 | 홈페이지 미리보기 | 답변 + 근거 출처 | 분개 목록, 장부 표, 검토 필요 항목 |
| 미리보기 | 실제 홈페이지 | 신청서 초안 | 장부·신고서 초안 |
| 승인 대상(외부 실행) | 공개 게시 | 민원 제출, 신청 제출 | 세무 신고 제출 |
| 작업 기록 | 수정 이력·버전 복원 | 상담·제출 이력 | 분개 변경·신고 이력 |
| 권한/DB | 학원 소유자 | 회원 권한 | 사업자별 권한 |

## 6. 사용자 승인 구조 (중요한 외부 실행)

작업을 세 등급으로 나눈다.

| 등급 | 예 | 처리 |
|---|---|---|
| 읽기 | 조회, 분석, 초안 생성 | 자동 수행 |
| 내부 쓰기 | 작업본 수정, 분개 초안, 신청서 초안 | 자동 수행 + 되돌리기 제공 |
| **외부 효과** | 홈페이지 게시, 민원·신청 제출, 세무 신고 제출 | **반드시 사용자 승인 후** 수행 |

외부 효과 작업의 규칙(설계):
1. UI가 아니라 **서버가 실행**한다. UI는 승인 결과만 전달한다.
2. 승인은 서버가 발급한 **1회용 토큰**으로 한다. 토큰은 승인 화면에 보인 **요약의 해시에 묶고**, 만료 시간을 둔다. 내용이 바뀌면 다시 승인받는다.
3. Playwright 같은 자동화는 **격리된 실행기**에서 승인 후에만 큐에 넣고, 최종 제출 직전 화면을 사용자에게 한 번 더 보여 준다(제출 직전 스냅샷 승인).
4. 모든 승인·실행은 **변경 불가 감사 기록**으로 남긴다(누가, 무엇을, 언제, 어떤 요약에 승인했는지).
5. 개인정보·금융정보는 최소만 수집하고 로그에는 마스킹한다.

## 7. BuildIt 1단계와의 관계

- 1단계(서버): 작업본 저장소, 게시 API, 비공개 미리보기. **UI 킷은 포함하지 않는다.**
- 2단계 이후(UI): BuildIt 화면을 만들 때 위 컴포넌트와 어댑터 구조로 만들고, BuildIt 전용 로직은 `buildit` 어댑터 안에만 둔다. 이렇게 하면 이후 서비스는 자기 어댑터만 추가하면 된다.
- 직접 편집과 AI 대화 수정을 함께 쓰는 데이터 연결(빌더 표현 ↔ 편집기 표현)은 별도 설계 문서로 다룬다.

## 8. 단계 계획 (공통 UI 관점)

| 단계 | 내용 | 승인 |
|---|---|---|
| BuildIt 1 | 작업본·게시·비공개 미리보기(서버) | 승인됨 |
| BuildIt 2 | 대화 화면을 공통 킷 구조로 구현(시작 화면, 대화, 미리보기 카드, 전체 화면) | 별도 승인 |
| BuildIt 3~5 | 대화 수정, 자료 첨부, 직접 편집 연결 | 별도 승인 |
| 공통 승인 모듈 | 승인 토큰·감사 기록(서버 공통 최소 계약) | NewStart·이지장부 착수 시 별도 승인 |
| NewStart / 이지장부 | 각 어댑터와 업무 기능 | 각각 별도 승인 |

## 9. 위험과 결정 사항

- **과설계 위험:** 공통화를 이유로 BuildIt 구현이 늦어지지 않게, 킷은 BuildIt에서 실제로 쓰는 컴포넌트부터 만들고 나머지는 인터페이스만 둔다.
- **독립성:** 킷에 서비스별 분기(`if buildit`)를 넣지 않는다. 필요하면 어댑터 기능(capabilities)으로 표현한다.
- **보안:** 승인 구조가 UI 안내에 그치지 않도록 서버 검증(1회용 토큰, 요약 해시)을 필수로 한다.
- **재무·민원 정보:** 이지장부와 NewStart는 개인정보·금융정보를 다루므로 BuildIt보다 엄격한 저장·로그 기준이 필요하다(해당 단계에서 별도 검토).
- **결정 필요:** 킷 배치 위치(저장소 내 공통 정적 모듈 경로), 커스텀 엘리먼트 사용 여부.
