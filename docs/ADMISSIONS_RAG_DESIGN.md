# 입시상담 RAG 검색 구조 개선안 + 학년도 기준 (설계안 — 구현 전, 승인 대기)

> 상태: **설계안**. 코드 구현은 승인 후 진행한다. 운영 DB 적재·APPROVED 승격·배포와 무관하다.
> 근거: 격리 환경 실측(2026-10-13) — 적재 480/57/66행이 상담 검색에서 조회되지 않음을 코드·실행으로 확인.

## 1. 현재 구조와 문제

`AdmissionsResearchService.research()`는 5단계만 조회한다.

| 단계 | 조회 대상 | 비고 |
|---|---|---|
| STEP1/2 | `admissions_knowledge_items` (ACTIVE, OFFICIAL, 확정/계획) | 현재 적재 9건(Q1~Q9 안내문, 사실 데이터 아님) |
| STEP3 | `admissions_official_materials` | **제목 키워드 LIKE만**. 상태 필터 없음 |
| STEP4 | `admissions_knowledge_items` (YOUTUBE) | 보조 의견 |
| STEP5 | `admissions_conflicts` (OPEN) | |

**조회되지 않는 테이블**: `admissions_departments`(480), `admissions_types`(57), `admissions_schedules`(66), `admissions_universities`(7).
→ "컴퓨터공학과 모집인원", "지역균형 지원자격", "원서접수 일정" 같은 사실 질문은 근거로 쓸 수 있는 행이 있어도 LLM 입력에 들어가지 않는다.
실측: 실제 LLM 22건 중 근거 0건 응답 4건(S17·S18·S21·S22)이 있었다(자세한 결과는 평가 보고 참조).

추가로 확인한 한계:
- 대학은 DB에 `name`만 저장(코드 `SNU` 등은 저장하지 않음) → 질문의 "서울대/서울대학교/SNU" 별칭 매핑이 필요.
- 일정은 `note`(문자열 "2026.9.7.(월) 10:00 ~ …")에 원문이 들어가고 `start_date/end_date`는 비어 있음 → 날짜 계산 질문은 원문 인용으로 제한.
- 전형 상세(`details`)에 모집인원/지원자격/전형방법/수능최저가 한 TEXT로 합쳐져 있음.
- STEP3은 상태 필터가 없어 DRAFT 자료 제목이 노출될 수 있다(자료 테이블에 status 컬럼이 없음).

## 2. 개선안: 질문 의도 → 조회 테이블 라우팅

질문에서 (대학, 학년도, 학과, 전형, 일정 키워드)를 규칙 기반으로 추출(LLM 호출 없음)한 뒤 의도별로 조회한다.

| 질문 의도 | 예시 | 1차 조회 | 2차(보조) | 반환 근거 |
|---|---|---|---|---|
| 대학 개요 | "연세대 수시 전형 종류" | `types`(대학+학년도) | `official_materials` | 전형명 목록 + 출처 자료 |
| 학과 모집 | "인하대 컴퓨터공학과 몇 명" | `departments`(대학+학년도+학과명 LIKE) | `types`(전형별 인원) | `quota_info` 행 그대로 + 출처 |
| 전형 요건 | "서울대 지역균형 지원자격/수능최저" | `types`(대학+학년도+전형명) | `official_materials` | `details`의 해당 항목만 |
| 일정 | "고려대 논술 원서접수 언제" | `schedules`(대학+학년도+제목 LIKE) | `official_materials` | `note` 원문 + 출처 자료 |
| 대학 비교 | "인하·고려·연세 컴공 비교" | `departments` 대학별 병렬 조회 | | 대학별 행을 나란히, 우열 판단 금지 |
| 학년도 변화 | "2028 달라지는 점" | `types/materials` 2028 | `knowledge`(계획) | "계획 단계" 라벨 필수 |
| 의견·전망 | "유튜브에서 …" | `knowledge`(YOUTUBE) | | "전문가 해석" 라벨 필수 |

공통 규칙:
1. **학년도 필터가 1순위**: 질문에 학년도가 없으면 2027(확정)로 가정하지 말고 답변에 "2027학년도 기준"이라고 명시하거나 되묻는다. 2027과 2028 근거를 한 문장에 섞지 않는다.
2. **상태 게이트**: 사실 테이블은 `verification_status`(NORMALIZED → 승인) 기준으로 승인된 행만 답변 근거로 쓴다. 승인 전(현재 전부 DRAFT/NORMALIZED)에는 "검증 중" 안내만 한다. 자료 테이블에는 status 컬럼이 없으므로 **V1066 수정(미병합 상태이므로 가능) 또는 V1067 추가**가 필요하다.
3. **근거 단위로 반환**: `Evidence`에 (테이블, 행 id, 학년도, 출처 자료 id/URL, 원문 값)을 담고 프롬프트에는 원문 값만 넣는다. LLM이 계산·추정하지 않도록 "근거에 없는 숫자는 쓰지 않는다"를 시스템 프롬프트와 후처리(출력 숫자 ⊂ 근거 숫자) 검증으로 이중 확인한다.
4. **데이터 없음 처리**: 라우팅된 테이블에서 행이 0건이면 LLM을 호출하지 않고 고정 문구("해당 대학·학년도 자료가 아직 없습니다")를 반환한다(현재도 근거 0건이면 LLM을 건너뛰지만, 가이드 안내문(Q1~Q9)만으로 LLM이 답을 만들어내는 경우를 막지 못한다). 안내문(knowledge)은 사실 근거가 아니라 **답변 형식 가이드**로 분류하고 근거 개수에 포함하지 않는다.
5. **금지**: 합격선·합격 확률·전년도 입결 생성, 한양대처럼 `null`로 보존된 필드를 추정으로 채우기.

구현 순서(제안): ① 대학/학년도/의도 추출기 + 단위 테스트 → ② `departments/types/schedules` 조회 서비스 → ③ Evidence 확장 → ④ 상태 게이트(마이그레이션) → ⑤ 22건 재평가.

### 허용 학년도(2027/2028) 정책 검토
- 현재 2027/2028 하드코딩 위치: 로더 `SUPPORTED_YEARS`, 검색의 "2027 확정/2028 계획" 분기(`year_confirmed`), 프롬프트·고정 문구.

- 권장(승인 후): `app.admissions.supported-years` 설정(연도별 상태 CONFIRMED/PLANNED)으로 외부화하고 `year_confirmed` 대신 `year_status` 열거형 도입. 2029는 전국 기본사항을 `PLANNED` + 별도 카테고리로만 허용하고 대학별 사실 질문에는 사용하지 않는다. 현재 2027/2028 한정은 현 자료 범위에서는 적절하다.

## 4. 구현 범위와 DB 변경 (확정안 — 구현·적용은 별도 승인 후)

> 운영 DB에는 아무것도 적용하지 않는다. 아래 변경은 격리 환경·CI에서만 검증하고, 운영 적용은 별도 승인 후 수동 배포 절차로만 진행한다.

### 4.1 DB 변경 (마이그레이션)
`V1066`은 미병합·운영 미적용이다. 다른 개발 DB에 이미 적용한 곳이 없으면 V1066을 수정하고, 있으면 `V1067`로 추가한다(적용된 V_파일 불변 원칙). 번호는 `docs/WORKFLOW.md` §4 기준으로 병합 직전에 재확인한다.

| 대상 | 변경 | 이유 |
|---|---|---|
| `admissions_official_materials` | `status VARCHAR(20) NOT NULL DEFAULT 'DRAFT'`, `verification_status VARCHAR(30)` 추가 | 현재 상태 컬럼이 없어 DRAFT 자료 제목이 검색에 노출됨 |
| `admissions_departments`, `admissions_types`, `admissions_schedules` | 동일한 `status`/`verification_status` + `source_material_id`(FK, schedules는 이미 있음) 추가 | 승인 게이트 + 근거 출처 인용(학과·전형은 출처 연결이 없음) |
| 세 테이블 | `row_hash CHAR(64) NOT NULL` + `UNIQUE (row_hash)` | DB 수준 멱등성(대학+학년도+이름+수치 해시). 원본 중복행(SNU 광역 2건)은 해시에 수치를 포함해 구분 |
| `admissions_universities` | 별칭 테이블 `admissions_university_alias(university_id, alias)` 신설, `UNIQUE(alias)` | "서울대/서울대학교/SNU" 질문 매핑(현재 DB에는 정식 이름만 있음) |
| `admissions_knowledge_items` | `role VARCHAR(10) NOT NULL DEFAULT 'FACT'` (`FACT`/`GUIDE`) | Q1~Q9 안내문을 근거 개수에서 제외 |
| 인덱스 | `(university_id, academic_year, status)` 복합 인덱스(세 테이블) | 의도별 조회 성능 |
| 일정 | `start_date/end_date` 파싱은 선택 사항(1차는 `note` 원문 인용) | 날짜 계산 질문은 범위 밖 |

연동 문서: `docs/DOMAIN.md`(스키마), `docs/API.md`(승인 API), Entity 동시 수정.

### 4.2 코드 구현 범위 (순서)
1. **질문 분석기** `AdmissionsQueryParser`(순수 함수): 대학(별칭), 학년도, 의도(학과/전형/일정/비교/변화/의견), 학과·전형 키워드 추출. 단위 테스트(given/when/then) 중심.
2. **조회 서비스** `AdmissionsFactSearchService`: 의도별로 `departments/types/schedules`를 `status=APPROVED` + 학년도 필터로 조회하고 `Evidence`(테이블, 행 id, 학년도, 출처 자료, 원문 값)로 반환.
3. **ResearchService 통합**: 기존 STEP1~5 앞에 FACT 단계 삽입. `GUIDE` 지식은 근거 개수에서 제외. 라우팅 결과 0건이면 LLM 호출 없이 고정 문구.
4. **프롬프트·후처리**: "근거에 없는 숫자 금지" 지시 + 출력 숫자 ⊂ 근거 숫자 검증, 위반 시 답변 대신 안전 문구.
5. **관리자 승인 API**: 행 단위 `DRAFT → REVIEW → APPROVED` 전환(감사 기록 포함). 자동 승격 없음.
6. **재평가**: 격리 CI에서 22건 재실행(자동 기준 + 접근 제한 아티팩트 수동 검토).

### 4.3 승인 필요 항목 / 하지 않는 것
- 운영 DB 마이그레이션 적용, 운영 데이터 적재, APPROVED 승격, 병합, 배포: **별도 승인 전 금지**.
- 학년도 허용 범위(2027/2028) 확장은 이번 범위에서 제외(§3 권고만 기록).

### 5.1 D1 설계 보완 (S22, 2026-10-13 확인) — 설계 보류, 기존 안전 정책은 변경하지 않음

D1(대학 미지정 2028 질문의 전면 거절)을 개선하려 할 때 아래 사실을 전제로 한다.

1. **연세대 2028 논술전형 수능최저 문구는 원본 파싱 요약에만 존재한다.** "논술전형 전 모집단위 수능최저 적용"은 `data/parsed/univ_sample/yonsei_2028_plan.json`의 `summary_2028` 요약 문구에만 있고, 적재 시드(`ipsi_seed_univ_sample.json`)의 2028 전형 행에는 없다.
2. **현재 적재된 연세 2028 전형 행은 학종 2건뿐이다.** 종합인재형(서류70+면접30, 수능최저 일부 모집단위 적용 — 언더우드 인문·사회/생명과학공학 미적용), 탐구인재형(서류60+면접40, 수능최저 미적용). 모집인원·지원자격은 null.
3. **따라서 논술 관련 2028 답변에는 별도의 공식 원문 확인과 적재가 필요하다.** 2028 시행계획 원문에서 해당 문구의 위치(쪽·표)를 확인하고, 전형 행(논술)으로 구조화해 DRAFT로 적재한 뒤 검증·승인(ACTIVE)해야 한다.
4. **근거가 확보되기 전에는 해당 내용을 답변에 사용하지 않는다.** 요약 문구, 유튜브 의견(YT-A012·A019 등), 정적 모범답안의 문장은 답변 근거가 아니다. D1을 구현하더라도 ACTIVE 행이 있는 범위(현재는 학종 2건)까지만 안내하고, 나머지는 미발표/미수집으로 구분해 답한다.

현 정책(S18·S20·S22 안전 정책)은 이 설계가 승인·구현·재평가될 때까지 그대로 유지한다.
