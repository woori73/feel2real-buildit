# 학원 상담신청(academy_inquiries) — 설계·개인정보 정책

## 범위(이번 버전)
공개 홈페이지 상담 접수 → 원장 목록 조회 → 상태 변경(신규/처리중/완료). **삭제 기능은 넣지 않는다.**

## 데이터와 격리
- 테이블 `academy_inquiries`(V1086, 신규 테이블만). 모든 조회·변경 쿼리에 `academy_id` 조건. 원장은 `academies.tutor_user_id`로 본인 학원만, ADMIN은 학원 id를 지정해 **조회만**.
- 다른 학원 접수 id로 변경을 시도하면 `404`(존재 여부 비노출).

## 수집·동의
- 수집 항목: 이름, 연락처, 문의 내용. 목적: 상담 안내. 동의 문구는 접수 폼에 표시되고 체크해야만 전송된다. 서버도 `consent=true`를 요구하고 `consent_version`·`consented_at`을 저장한다(문구 변경 시 `AcademyInquiry.CONSENT_VERSION`을 올린다).
- 연락처는 숫자만 저장, 이름·문의는 제어문자 제거. 화면에는 항상 `textContent`로 출력(XSS).

## 스팸·남용 방어
함정 입력칸, 같은 연락처 10분 중복 무시, IP 분/시간 제한, 전역 일일 상한, 학원별 일일 상한(50), 링크 1개 제한. 제한기는 입시상담과 같은 IP 판별 규칙을 쓰되 한도·기록은 분리한다. 카운터는 JVM 메모리(인스턴스별, 재시작 시 초기화).

## 로그
접수 id·학원 id·결과만 기록. 이름·연락처·문의 본문은 로그·오류 메시지에 싣지 않는다(단위 테스트로 고정).

## 보관·삭제 정책(정책 수립 — 구현은 후속)
- **보관 기간: 접수일로부터 1년**(`retention_until`). 완료 처리와 무관하게 1년 후 파기 대상.
- **파기 방식(후속 구현 제안)**: 일 1회 배치가 `retention_until < 오늘 AND anonymized_at IS NULL`인 행의 `name/phone/message`를 NULL로 비우고 `anonymized_at`을 기록(통계용 행·상태는 유지). 화면에는 "(삭제된 문의)"로 표시된다(이미 지원).
- **정보주체 삭제 요청 처리 설계(후속)**: ① 접수 경로: 학원 원장 또는 운영 문의 채널 → ② 본인 확인: 접수 당시 연락처 일치 확인(원장이 확인) → ③ 처리: ADMIN 전용 내부 도구/SQL 절차로 **해당 행 익명화**(위 파기와 동일 연산, `anonymized_at` 기록, 처리자·사유 감사 로그) → ④ 처리 결과를 요청자에게 회신. 행 삭제 대신 익명화를 쓰는 이유는 학원별 통계·감사 기록 유지와 FK 안전성. 학원 삭제 시에는 FK `ON DELETE CASCADE`로 접수도 함께 삭제된다.
- 원장 화면에 보관 안내를 표시한다.

## 한계/후속
- 배치 파기·익명화 도구·관리자 삭제 요청 처리 UI는 미구현(설계만).
- 알림(이메일·문자)은 없음: 원장이 목록에서 확인. 신규 건수는 목록 화면에 표시.
- 운영 DB 마이그레이션(V1086)은 배포 승인 후 적용된다. 이 PR은 마이그레이션을 운영에 적용하지 않는다.
