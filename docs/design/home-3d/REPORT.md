## 1. 기존 홈페이지 조사 (최신 main 기준)

| 항목 | 확인 결과 |

## 2. 3D 기술 비교와 선택

측정 환경: npm 최신 패키지를 esbuild로 번들·압축, gzip -9 (2026-10-22).

| 후보 | 실측/확인 | 라이선스 | 평가 |
|---|---|---|---|
| Three.js 0.186 | 최소 장면(렌더러·카메라·메쉬·물리 재질)만 트리 셰이킹해도 **537KB / gzip 134KB** | MIT | 표현력 최고. 이 홈의 3D는 오브젝트 1개라 과함. 첫 화면 비용·유지 부담이 큼 |
| React Three Fiber | React 전제 | MIT | 이 프로젝트는 Thymeleaf SSR이라 **해당 없음** |
| Spline | 런타임 npm 36MB(압축 전 패키지), 장면 파일은 외부 호스팅·디자이너 계정 의존 | 런타임 라이선스 필드 미표기, 장면은 Spline 서비스 약관 | 자산 소유·가용성·성능 리스크. 불채택 |
| GSAP 3.15 | core **73KB / gzip 28KB**, ScrollTrigger +45KB / gzip 18KB | "Standard 'no charge' license"(무료, 조건은 gsap.com/standard-license 확인 필요) | 필요한 연출은 IntersectionObserver·CSS 변수로 충분. 불채택 |
| CSS 3D Transform | 0KB | — | 카드·배너 깊이감에 최적, 모든 기기에서 안정 |
| **자체 WebGL(채택)** | 보석·링·입자 셰이더 포함 JS 합계 **약 23KB(압축 전)** | 자체 코드 | 의존성 0, 지연 로딩·중지·복구를 직접 통제 |

**결정:** CSS 3D(카드·배너·시차) + 직접 작성한 작은 WebGL(히어로 보석). 라이브러리를 추가하지 않는다.
**대안 기준:** 이후 3D 오브젝트가 여러 개로 늘거나 모델 파일(glTF)이 필요해지면 Three.js를 지연 로딩하는 방식으로 재검토한다.

### 성능 측정 — 작업 전(main `1c639505`) vs 작업 후, 같은 환경·각 3회 평균
측정 환경: 로컬 격리 DB, 헤드리스 Chromium, **SwiftShader 소프트웨어 GL**(실제 GPU 아님), 모바일은 CPU 4배 감속. 외부 폰트·GTM은 샌드박스 망 제한으로 양쪽 모두 로드되지 않음. 스크립트: `qa/perf-home-3d.js`.

| 환경 | 구분 | FCP=LCP (ms) | CLS | TBT 추정 (ms) | 롱태스크 |
|---|---|---|---|---|---|
| 데스크톱 1440 | 작업 전 | 580 (520~628) | 0.0033 | 92 (82~98) | 1 |
| 데스크톱 1440 | 작업 후(WebGL) | 680 (640~732) | 0.0033 | 228 (214~241) | 3 |
| 데스크톱 1440, reduced motion | 작업 전 | 611 | 0.0033 | 50 | 1~2 |
| 데스크톱 1440, reduced motion | 작업 후(정적) | 640 | 0.0033 | 78 | 2 |
| 모바일 390, CPU 4배 | 작업 전 | 1023 (956~1124) | 0 | 475 (417~569) | 2 |
| 모바일 390, CPU 4배 | 작업 후(WebGL) | 약 1100 (1012~1264) | 0 | 약 645 (616~665)* | 4~5 |

\* 터치 기기 초기화를 로딩 완료 후로 미루는 보완 적용 후 3회(적용 전 654~739ms).

해석:
- **Core Web Vitals:** LCP는 작업 전후 모두 같은 요소(AI AGENT 배너 이미지)이고 2.5초 기준을 크게 밑돈다. CLS는 0.0033 이하로 기준(0.1)보다 훨씬 낮다. INP는 합성 환경에서 측정하지 못했다.
- **비용:** WebGL을 켠 데스크톱은 LCP +약 100ms(+17%), TBT +약 136ms. 모바일(감속)은 TBT +약 170ms. 정적 모드는 작업 전과 거의 같다(LCP +29ms, TBT +28ms).
- **주의:** 모바일 TBT 약 645ms는 Lighthouse의 "나쁨" 구간(600ms 초과)이다. CPU로 GL을 흉내 내는 환경이라 과대 추정일 가능성이 크지만, **실제 저가 안드로이드·iOS에서 Lighthouse로 확인하기 전에는 배포하면 안 된다.** 기준 미달이면 터치 기기에서 WebGL을 기본 끄고 SVG 보석만 쓰도록 `decideRenderMode`만 바꾸면 된다(한 줄).
- 3D 자산 전송량(압축 전): CSS 12.7KB + core 6.7KB + main 약 17KB = **약 36KB**(gzip 시 약 10KB 예상, 로컬 서버는 압축 미적용).

### 빌더·게시 페이지 회귀
- 이번 변경은 `public/landing.html`과 홈 전용 신규 정적 파일뿐이다. `/builder`·`/academies/*` 템플릿, 빌더 JS·CSS, 로고 버튼·편집·저장·게시 코드는 **한 줄도 수정하지 않았다.** `landing_3d.*`는 홈에서만 로드된다.
- 확인한 것: `/builder` 응답 200, 홈→빌더 링크(칩·카드) 동작, 기존 빌더 관련 JS 테스트(CI 목록) 통과 여부는 CI에서 확인.
- **확인하지 못한 것:** 로그인 상태의 빌더 편집·저장·게시 실조작. 계정이 없어 이 환경에서는 불가하며 배포 전 사람이 확인해야 한다.

## 7. 한계와 남은 위험

1. 운영 도메인 접속·실기기 측정·로그인 기반 회귀는 이 환경에서 못 했다(위 표시).
2. 작업 전후 대조는 소프트웨어 GL 환경 기준이다. 실기기 Lighthouse 전/후 비교가 필요하다.
3. WebGL 보석은 장식이다. 첫 방문 인상은 개선되지만 전환율 효과는 측정 전이다.
4. `AcademyCraft` 카드는 로그인 필요 서비스라 비회원에게는 로그인 화면으로 이어질 수 있다(배지 "원장·강사 로그인"으로 표기).
5. 입시상담 AI 카드는 "베타"로 표기. 자료 반영과 공개 범위가 확정되면 문구를 갱신해야 한다.

## 8. 빌더 3D 적용 가능성 검토 (C)

- 지금은 **적용하지 않는다.** 빌더는 편집·저장·게시가 핵심이라 회귀 위험이 이득보다 크다.
- 적용한다면 단계적으로: ① 게시 페이지(공개 영역)의 카드 컴포넌트에 `f3d-card` 틸트·등장만 옵트인(WebGL 제외) ② 빌더 편집 화면은 제외 ③ 로고 버튼·편집·저장·게시 회귀 테스트(현재 CI의 `academy_builder_*` JS 테스트 + 실브라우저 시나리오)를 먼저 확장.
- 필요 작업: 토큰·카드 컴포넌트를 `landing_3d.css`에서 분리한 공용 파일화.
