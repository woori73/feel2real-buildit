## 1. 원칙

- F2R은 **돈을 받거나 보내지 않는다.** 기존 수납 원칙("실제 결제·송금은 하지 않는다")을 그대로 둔다. 이번에 더한 것은 ① 학부모에게 금액과 학원 계좌를 안내하는 링크 ② 이미 수집된 통장 입금과 청구를 맞춰 보고 납부 기록을 대신 적어 주는 것뿐이다.
- 카드번호·계좌 비밀번호 같은 결제 수단 정보를 받거나 저장하지 않는다. 저장하는 계좌번호는 학부모에게 안내할 **학원 수납 계좌**다.
- 실제 결제 대행사 호출·실제 키는 없다. 결제창 흐름은 돈이 움직이지 않는 가짜 구현(`FakeTuitionPaymentGateway`)만 있다.
- 장부(`easy_transactions`)는 **읽기만** 한다. 입금 대조는 장부 거래를 만들거나 고치지 않는다(EASY 원칙 §13: 은행 입출금은 수입으로 넣지 않는다 — 수강료 수입은 여전히 카드매출·현금영수증 자료로 잡는다).
- 스위치 `app.payment.enabled`(환경변수 `F2R_PAYMENT_ENABLED`) 기본 `false`. 운영 설정은 건드리지 않았다. 꺼져 있으면 `/pay/**`와 `/api/admin/easy/billing/**`(status 제외)는 404다.

## 2. 기존 기능 확인 결과 (코드 기준)

| 확인한 것 | 결과 | 근거 |
|---|---|---|
| 수강료 청구·납부 기록 | `easy_tuition_payments`에 학생·사업체·월별 1행. 청구액·납부액을 원장이 손으로 적고 상태(미납/일부납/완납)는 계산값 | `EasyTuitionService`, `EasyTuitionController`(`/api/admin/easy/payments`), `CoordTuitionActions`(MCP `f2r_tuition_change`) |
| 실제 결제 | 없음. 삭제는 물리 삭제 | `EasyTuitionService.delete` |
| 은행 거래 수집 방식 | **수동 내려받기**가 현재 경로다. 원장이 은행 사이트에 직접 로그인해 거래내역을 파일로 받고, AI가 행 단위로 정리해 MCP `save_easy_site_rows`로 저장한다 | `EasySiteCollectionService`, `EasySiteCollectionCatalog` |
| 얼마나 자주 가능한가 | 횟수 제한은 없다 — 원장이 내려받을 때마다. 한 번에 최대 2,000행·조회 기간 최대 366일. 사람이 로그인해야 하므로 사실상 "원장이 할 때"가 주기다 | `EasySiteCollectionService.MAX_ROWS`, `MAX_PERIOD_DAYS` |
| 자동 수집 | 은행 자동 조회 어댑터(`CODEF_BANK`)와 매일 02:30 크론은 코드에 있지만, `easy.collection.verified-sources` 기본값이 비어 있어 **어떤 수집원도 자동 실행되지 않는다**(계약·키·검증 전) | `EasyCollectionSchedulerService`, `EasyCollectionProviderReadinessPolicy`, `V1105` |
| 수집된 입금이 저장되는 곳 | `easy_transactions`에 `direction=INCOME`, `pay_method='계좌'`, 보낸 사람은 `counterparty`, 적요는 `description`. 6자리 이상 연속 숫자는 끝 4자리만 남긴다 | `EasySiteCollectionService`(buildRow) |
| 입금 분류 | 카드 정산·대출·지원금 등은 판정하고, 10만원 이상 계좌 입금에는 현금영수증 검토 메모를 붙인다. 수강료 여부는 판정하지 않는다 | `EasyBankTransactionClassifier` |

결론: 입금 확인의 빠르기는 **원장이 통장 내역을 얼마나 자주 올리느냐**에 달려 있다. 자동 수집을 붙이려면 계약·비용·사업자등록 문제가 먼저다(연구 문서 2.1).

## 3. 만든 흐름

### 3.1 계좌 입금 + 자동 대조 (1순위)

1. 원장이 수납 관리에서 청구를 등록한다(기존 기능).
2. `/easy/billing`에서 그 청구의 **링크**를 만든다. 은행·계좌·예금주·기한(기본 14일, 최대 60일)을 적는다. 주소는 만든 직후 한 번만 보인다.
3. 학부모가 링크(`/pay/{토큰}`)를 로그인 없이 연다. 보이는 것: 학원 이름, 가린 학생 이름(`김*수`), 대상 월, 청구 금액·낼 금액, 은행·계좌·예금주, **입금자명에 붙일 숫자 4자리**, 기한, 환불·영수증 안내.
4. 원장이 통장 내역을 올린 뒤(기존 수집) `/easy/billing`에서 **대조 실행**을 누른다.
5. 확실한 입금만 납부 기록에 더해지고, 애매한 입금은 **확인이 필요한 입금** 목록에 남는다.

대조 규칙(`TuitionDepositMatcher`, 순수 계산):

| 입금 상태 | 처리 |
|---|---|
| 금액 = 남은 청구액, 적요·보낸 사람에 확인 번호가 있음, 맞는 청구 1개, 그 청구에 맞는 입금 1개 | **자동 기록** (`CODE_AMOUNT`) |
| 금액 = 남은 청구액, 학생 이름이 있음, 위와 같은 유일 조건 | **자동 기록** (`NAME_AMOUNT`) |
| 번호나 이름은 있는데 금액이 다름 | 원장 확인 (`AMOUNT_MISMATCH`) |
| 금액만 같음 | 원장 확인 (`AMOUNT_ONLY`) |
| 맞는 청구가 둘 이상 | 원장 확인, 후보 없음 (`MULTIPLE_BILLS`) |
| 한 청구에 자동 후보 입금이 둘 이상 | 모두 원장 확인 (`MULTIPLE_DEPOSITS`) |
| 번호·이름·금액 어느 것도 안 맞음 | 목록에 넣지 않음 |

- 대상 입금: `easy_transactions` 중 수입 방향, 결제수단 `계좌`/`계좌이체`, 링크를 만든 날~기한 사이.
- 확인 번호는 다른 숫자에 붙어 있으면 인정하지 않는다(금액·계좌 끝자리와 혼동 방지).
- 중복 방지: 입금 1건은 대조 행 1개만 가진다(`txn_id` UNIQUE). 대조를 몇 번 실행해도 같은 입금은 다시 기록되지 않는다.
- 자동 기록 직전에 수납 행을 잠그고 남은 금액을 다시 확인한다.

원장이 할 수 있는 일: 확인 목록에서 **납부로 기록**(남은 청구액보다 큰 입금은 거절) / **수강료 아님** / 기록된 입금 **기록 취소**(더한 금액을 빼고 확인 목록으로).

### 3.2 결제창 뼈대 (2순위, 시험)

`app.payment.card-test`(환경변수 `F2R_PAYMENT_CARD_TEST`)까지 켜야 보인다.

1. 청구 화면의 "결제창 열기(시험)" → 서버가 주문을 만든다. **금액은 요청에서 받지 않고 서버의 남은 청구액**으로 정한다.
2. 시험 결제창(`/pay/{토큰}/test-checkout`) — 실제 대행사 결제창이 들어설 자리. 카드 정보를 받지 않고 성공·실패만 고른다.
3. 성공 주소로 돌아오면 서버가 ① 주문이 이 링크의 것인지 ② 브라우저가 보낸 금액이 주문 금액과 같은지 ③ 주문 금액이 지금 남은 청구액과 같은지 확인하고, 대행사 승인(가짜 구현)을 거쳐 납부 기록에 더한다.
4. 같은 확인이 다시 와도(새로고침, 대행사 알림 `/pay/notify`) 이미 결제된 주문이면 아무것도 바꾸지 않는다. 주문 행을 잠그고 처리한다.

`TuitionPaymentGateway` 인터페이스가 대행사 자리다. 실제 대행사는 계약·대표 승인 뒤 별도 구현으로 붙인다. 그때 손볼 것: 대행사 승인 호출을 DB 잠금 밖으로 옮기기, 알림 서명 검증을 그 회사 방식으로 바꾸기, 취소·환불 API.

### 3.3 공개 주소 보호

- 토큰: 256비트 난수(43자). DB에는 SHA-256 해시만. 없는 토큰·회수·만료는 구분 없이 404.
- 요청 제한: IP당 분당 30회(`TuitionPayRateLimiter`, 기록 IP 5,000개 상한). 프록시 뒤 실제 IP는 기존 신뢰 프록시 판정(`AdmissionsRateLimiter.resolveClientIp`)을 그대로 쓴다.
- 응답 헤더: `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex`.
- 응답 내용: 학생 실명·연락처 없음.
- `SecurityConfig`: **바꾸지 않았다.** `/pay/**`는 화면 주소라 기존 맨 끝 규칙(화면은 공개)에 해당하고, 관리 API는 기존 `/api/admin/**` → 관리자 규칙에 해당한다. 테스트로 확인했다(비로그인 관리 API 401, 스위치 OFF 404).

## 4. 만들기·고치기·지우기 범위와 삭제 정책

| 대상 | 만들기 | 고치기 | 지우기 | 권한 |
|---|---|---|---|---|
| 청구 링크 `easy_tuition_bill_links` | 원장 | **없음** — 금액은 수납에서 고치고, 계좌·기한을 바꾸려면 새로 만든다(이전 링크는 자동 회수) | **회수(soft)**: 행은 남기고 `REVOKED`. 물리 삭제는 수납이 지워질 때만(CASCADE) | 관리자 |
| 입금 대조 `easy_tuition_deposit_matches` | 대조 실행 시 서버가 만듦 | 상태만: 확정 / 수강료 아님 / 기록 취소 | **없음**. 수납이 지워지면 같이 지워져(CASCADE) 그 입금은 다시 대조 대상이 된다 | 관리자 |
| 시험 주문 `easy_tuition_pg_orders` | 학부모가 결제창을 열 때 서버가 만듦 | 상태만(READY→PAID/FAILED) | **없음**. 수납·링크가 지워지면 같이 지워진다(CASCADE) | 공개(토큰 보유자) |

고치기를 만들지 않은 이유: 링크는 이미 학부모에게 보낸 안내라, 내용을 바꾸는 것보다 회수하고 새로 보내는 편이 "어떤 안내를 보고 입금했는지"가 분명하다.

주의할 점: 수납 삭제 시 CASCADE는 **시험 모드라서** 택한 정책이다. 실제 결제가 붙으면 결제된 주문이 있는 수납은 삭제를 막아야 한다(아래 대표 결정 5번).

## 5. 대표가 정할 것

1. **결제 방식**: 계좌 입금+대조만으로 갈지, 카드·가상계좌·CMS·제로페이를 더할지. 카드는 일반 등급 2.9~3.5%, 가상계좌는 건당 200~400원(공식 페이지 확인). CMS·제로페이 수치는 원문 미대조.
2. **가입 주체**: 본인 명의 사업자등록 여부. 계좌 직접 입금 외의 방식은 대부분 사업자등록이 전제다. KG이니시스 구비서류에만 "개인비사업자" 항목이 있는데 허용 범위는 상담으로 확인해야 한다.
3. **수수료 부담**: 카드 수수료가 생기면 학원이 부담하는지. (학부모에게 넘길 수 있는지는 법적 확인이 필요 — 이번 조사 범위 밖)
4. **환불 정책 표시**: 청구 화면에 학원의 반환 기준 전문을 넣을지, 지금처럼 "학원에 문의"만 둘지. 환불 처리 자체(금액 계산·기록)를 F2R에 만들지.
5. **삭제·취소 정책**: 수납을 지우면 링크·대조·주문이 같이 지워지는 지금 방식(시험용)을 유지할지, 납부 기록이 있으면 삭제를 막을지. 입금 대조 기록을 얼마 동안 보관할지.
6. **애매한 입금 처리**: 지금은 "번호+금액" 또는 "학생 이름+금액"이 유일하게 맞을 때만 자동 기록한다. 이름 기준 자동 기록을 꺼서 번호가 있을 때만 자동으로 할지, 금액만 같은 입금을 확인 목록에 올릴지 말지.
7. **입금 확인 주기**: 원장이 통장 내역을 올릴 때만 확인되는 지금 방식으로 충분한지, 자동 수집(계약·비용 발생)을 검토할지.
8. **현금영수증·영수증**: 발급 기록을 F2R에서 관리할지(지금은 안내 문구와 검토 메모만 있음).
9. **학부모에게 링크를 보내는 방법**: 지금은 원장이 주소를 복사해 직접 보낸다. 기존 학부모 안내(카카오톡 공유) 흐름에 붙일지.

## 6. 이번에 하지 않은 것

- 실제 대행사 연동·실제 결제·환불.
- 통장 내역을 올릴 때 대조를 자동으로 돌리는 것(지금은 버튼). 수집 경로 코드는 건드리지 않았다.
- CODEF 자동 수집으로 들어온 입금 대조(그 경로는 결제수단 값이 달라 대상에서 빠진다. 자동 수집 자체가 꺼져 있다).
- MCP 도구(`f2r_tuition_*`)에 청구 링크 만들기 추가.
- 현금영수증·영수증 발급 기록.
